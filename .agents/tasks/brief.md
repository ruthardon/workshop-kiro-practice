## 1. Stack y Docker (docker-compose.yml en la raíz)
3 servicios con healthchecks y volúmenes persistentes (volumen nombrado para postgres):
- db: PostgreSQL 16 con db/init.sql (montado en /docker-entrypoint-initdb.d) que cree tablas policies, claims, claim_audits y cargue seeds realistas: al menos 5 pólizas (activas, expiradas, distintos deducibles; campos: holder_name, national_id, phone, email, policy_number, status ACTIVE/EXPIRED, start_date, end_date, deductible NUMERIC(12,2), coverage_limit NUMERIC) y 8 siniestros en estados OPEN, APPROVED, REJECTED, CLOSED (claims: id, policy_id FK, description, incident_date, claimed_amount NUMERIC(12,2), indemnity_amount NUMERIC(12,2), status, closed_at, reopen_count INT default 0, created_at...). claim_audits: id, claim_id, old_status, new_status, changed_by, reason, created_at. Incluir audits seed coherentes. NUMERIC para dinero.
- backend: Node.js + Express + TypeScript. Carpeta backend/ con src/routes, src/controllers, src/services, src/middleware (errorHandler centralizado), src/config (db con pg, swagger). Swagger UI en /api-docs (swagger-jsdoc + swagger-ui-express) con anotaciones en las rutas. Formato de respuesta { success, data, error }. Endpoints: GET /api/health, GET /api/policies, GET /api/policies/:id, GET /api/claims (filtro ?status=), GET /api/claims/:id, POST /api/claims, PATCH /api/claims/:id/approve, PATCH /api/claims/:id/reject (ambos registran en claim_audits), GET /api/claims/stats (o KPIs calculables en front). CORS habilitado. Dockerfile (multi-stage o simple con tsc/tsx, usuario no root si es simple). sonar-project.properties en la RAÍZ (sonar.projectKey=claimshield, sources=backend/src,frontend/src, exclusiones node_modules/dist, lcov path opcional, host http://localhost:9000). Script de test setup mínimo en backend (vitest o jest + supertest) con package.json scripts (build, start, dev, test) para que los alumnos escriban tests que fallan; NO añadir tests que cubran los bugs.
- frontend: React + Vite + TypeScript + TailwindCSS (Dockerfile; vite dev --host o build+nginx, lo más simple; puerto 5173). Dashboard limpio: cabecera con 3 tarjetas KPI (Total Siniestros, Monto Reservado, Siniestros Abiertos), tabla filtrable por estado (y búsqueda), modal "Reportar siniestro" (selector de póliza, descripción, fecha incidente, monto reclamado), botones Aprobar/Rechazar en filas OPEN, badges de estado coloreados. Accesible (labels, aria, foco en modal).
Puertos: frontend 5173, backend 3000, db 5432 (expuesto). Variables de entorno en docker-compose; incluir .env.example, .gitignore (incluye node_modules), .dockerignore.

## 2. Bugs intencionales (NO corregirlos; implementarlos tal cual; NO dejar comentarios que los delaten como BUG/SEC en el código fuente, a lo sumo comentarios neutros; documentarlos solo en README/backlog)
- BUG-101 (Indemnización): en el servicio de creación/cálculo de siniestros, indemnity = claimed_amount - deductible directo, sin validar claimed < deductible -> indemnizaciones negativas guardadas en BD.
- BUG-102 (Vigencia): POST /api/claims permite crear siniestros sobre pólizas EXPIRED o con incident_date fuera de [start_date, end_date]. No se valida nada de eso.
- SEC-103 (Seguridad y code smells): (a) GET /api/policies/:id devuelve national_id, phone y email en texto plano sin enmascarar. (b) Crear processClaimLegacy() en el servicio de siniestros con alta complejidad ciclomática (muchos if/else anidados), variables sin usar, console.log imprimiendo datos sensibles de la póliza (national_id, policy_number completo, email) y bloques catch (e) {} vacíos. Debe compilar sin errores (tsconfig noUnusedLocals false) y estar exportada/usada de modo que Sonar la detecte (p. ej. invocada en una ruta o exportada).
- BUG-104 (Frontend): al aprobar/rechazar, la fila actualiza su badge pero el KPI "Monto Reservado" NO se recalcula hasta recargar (F5). Implementarlo de forma natural y realista, no obvia (p. ej. KPIs calculados una sola vez en useEffect/useState inicial, o memo con dependencias incorrectas, mientras la fila se actualiza por estado local).
Los demás flujos deben funcionar correctamente (aprobar/rechazar con auditoría en claim_audits, filtros, listados). No debe haber otros bugs.

## 3. Configuración Kiro (.kiro/)
Steerings en .kiro/steering/ (front-matter `inclusion: always`):
- insurance-domain.md: tipos exactos/decimales para montos y deducibles (NUMERIC en BD, nunca float; en JS strings/decimal lib o centavos enteros), prohibición de indemnizaciones negativas (max(0, reclamado - deducible), y tope coverage_limit), obligatoriedad de registrar todo cambio de estado en claim_audits, validación de vigencia de póliza, máquina de estados permitida.
- security-pii.md: enmascarar PII como ***-**-1234 en respuestas API (ejemplos para national_id, teléfono, email), prohibición absoluta de loguear datos personales o números de póliza completos, qué sí se puede loguear (ids internos, últimos 4).
- api-standards.md: formato { success, data, error }, manejo centralizado de errores HTTP 400, 404, 409, 422 (cuándo usar cada uno, formato de error con code y message), documentación Swagger obligatoria por endpoint.
Hooks en .kiro/hooks/ (formato v1 JSON: {"version":"v1","hooks":[{name,trigger,matcher,action}]}):
- sync-swagger-on-route-change.json: trigger PostFileSave, matcher regex que cubra backend/src/routes/ (p. ej. backend/src/routes/.*\\.ts$), action type "agent" con prompt que instruya verificar y actualizar esquemas/anotaciones Swagger correspondientes.
- check-pii-on-save.json: PostFileSave, matcher backend/src/.*\\.ts$, action agent con prompt que revise que no se hayan introducido console.log con datos sensibles (national_id, phone, email, policy_number, etc.) y proponga reemplazo seguro.
Workflows en .kiro/workflows/ como markdown:
- design-and-build-endpoint.md: pasos: 1) diagrama de secuencia con power Draw.io, 2) actualizar esquema BD si aplica (init.sql + migración), 3) implementar controlador/servicio bajo los steerings, 4) actualizar Swagger, 5) generar colección de pruebas con power Postman, 6) validar calidad con power SonarQube. Cada paso con entregable y criterio de salida accionable.
- fix-bug-ticket.md: diagnosticar, escribir primero el test que falla, aplicar fix respetando steerings, verificar con SonarQube; con checklist.
